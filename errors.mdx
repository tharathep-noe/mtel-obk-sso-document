All errors are returned by a single exception filter.

```json
{
  "error": {
    "statusCode": "SSO_IDP_001",
    "message": "Identity already exists.",
    "stack": "... (non-production environments only)"
  }
}
```

<Warning>
  Always branch on `error.statusCode`, never on `error.message`. Some messages are overridden at runtime and some contain typos carried over from the service.
</Warning>

`error.statusCode` holds the application error code as a string for known business errors, or the numeric HTTP status for validation and framework errors.

## Status codes

| Status | Meaning | What to do |
| --- | --- | --- |
| 200 / 201 | Success. 201 is returned by `POST /user/register` only | - |
| 204 | Success with no body. Returned by `PUT /accounts/delete/` | - |
| 400 | Validation or business error. `error.details.errors` is present for schema failures | Fix the payload |
| 401 | Missing or invalid credentials, or an expired access token | Refresh the token, or check the credentials for that environment |
| 422 | Identity exists in both IAM and Buzzebee | Prompt the user to merge, or retry with `options.auto_merge = true` |
| 429 | OTP request limit reached for the identifier | Wait for the rolling hour window |
| 500 | Server error, or a business error mapped to 500 | Retry, then contact the SSO team |

## Retry policy

<Steps>
  <Step title="Await every response">Do not fire-and-forget. Wait for each response before issuing the next request for the same user.</Step>
  <Step title="Classify the failure">Retry only transport failures, 429 and 5xx. Never retry a 4xx validation error.</Step>
  <Step title="Back off">For 429 wait for the rolling hour window. For 5xx use exponential back-off with jitter, maximum 3 attempts.</Step>
  <Step title="Refresh once on 401">Refresh the access token and replay the request a single time.</Step>
  <Step title="Log correlation data">Record the endpoint, `publicId`, timestamp and `error.statusCode`.</Step>
</Steps>
